# ARGUS 4-5 — 일반계정 권한 상승 가능성 (Access Control) 자동 진단 엔진

> ARGUS 플랫폼의 취약점 진단 항목 중 "4-5: 일반계정 권한 상승 가능성"을 담당하는 모듈. 실제 테스트 계정으로 로그인해서, 일반 사용자가 관리자 API에 접근할 수 있는지 / 다른 사용자의 자원을 볼 수 있는지 / 요청에 몰래 role 값을 끼워 넣으면 서버가 그대로 받아주는지를 실제로 찔러보고 검증한다.

---

## 1. 한 줄 요약

**"일반 사용자 계정 두 개를 준비해서, 한쪽(A)이 관리자 영역에 들어가지는지 / 다른 쪽(B)의 자원을 몰래 볼 수 있는지 / 요청에 `role=ADMIN` 같은 값을 끼워 넣으면 서버가 그대로 받아주는지"를 실제 HTTP 요청으로 검증하는 엔진이다. 이상한 코드를 "심어서" 반응을 보는 방식이 아니라, **권한 경계 자체를 실제로 넘어보는** 방식이라 판정 기준이 독특하다.

| 그룹 | 파일 | 역할 |
|---|---|---|
| 엔진 핵심 | `scanner.py` | 전체 엔진. `run_g45_scan()`이 5단계(Phase 0/0.5/1/2/4/정리)를 순서대로 실행하고 finding까지 직접 만든다 |
| 엔진 핵심 | `g45_discovery.py` | 자원 인벤토리 수집 — 계정별로 "이 계정이 볼 수 있는 자원 id 목록"을 만든다 (수동 조회 + 부족하면 능동 생성) |
| 엔진 핵심 | `g45_auth.py` | 인증 헤더 구성 + 상대방 계정의 진짜 식별자(id)를 알아내는 로직 |
| 엔진 핵심 | `g45_payloads.py` | 안전한 더미 요청 본문 생성 (엉뚱한 값을 보내 예외를 만들지 않기 위함) |
| 엔진 핵심 | `g45_utils.py` | id 추출, "응답에 주입값이 그대로 반영됐는지" 재귀 확인, api-tree 로더 |
| 엔진 핵심 | `g45_models.py` | 결과를 담는 단순 데이터 구조 |
| 백엔드 통합 | `module.py` | 진단 모듈 레지스트리 진입점 (`G45Module`) |
| 백엔드 통합 | `manifest.yaml` | 모듈 메타데이터 |

> 파일 구성은 전체 합쳐서 ~900줄 정도로 작은 편이지만, **핵심 판단 로직은 전부 `scanner.py` 한 파일에 몰려 있다.** 처음부터 ARGUS 전용으로 새로 짠 모듈이라 별도 레거시 엔진을 감싸는 구조는 아니다.

## 2. 왜 이 취약점을 진단하는가 (배경 지식)

"권한 상승(Privilege Escalation)"은 크게 두 방향으로 갈린다.

- **수직 권한 상승 (Vertical)**: 일반 사용자가 **관리자만 써야 할 API**에 접근하는 것. 서버가 "이 요청을 보낸 사람이 관리자인지"를 제대로 안 따지면 발생한다.
- **수평 권한 상승 (Horizontal) — IDOR / BOLA**: 같은 등급의 사용자끼리, **다른 사람의 자원**에 접근하는 것. 예를 들어 `주문 조회` API가 "이 주문이 진짜 나(로그인한 사람)의 것인지"를 안 따지고 그냥 id만 맞으면 보여주면 발생한다. (`IDOR` = Insecure Direct Object Reference, `BOLA` = Broken Object Level Authorization — 같은 현상을 부르는 다른 이름)
- **Mass Assignment**: 회원가입/프로필 수정 같은 요청에 서버가 원래 받으려던 필드 외에, 클라이언트가 **추가로 끼워 넣은 필드까지 그대로 받아서 저장**해버리는 것. 예를 들어 `{"nickname": "abc"}`만 받아야 하는데 `{"nickname": "abc", "role": "ADMIN"}`을 보냈을 때 서버가 `role`까지 그대로 반영하면, 회원가입만으로 관리자가 될 수 있다.

세 가지 모두 "서버가 **누가 요청했는지, 그 사람이 이걸 해도 되는지**를 제대로 확인하지 않는다"는 공통 원인에서 나온다. 그래서 이 엔진은 XSS 스캐너처럼 "이상한 문자열을 심어서 반응을 본다"가 아니라, **실제로 계정 두 개를 놓고 권한 경계를 넘어보는 방식**으로 동작한다.

## 3. 전체 파이프라인

```
[준비] 계정 로그인 + api-tree 로드
        ↓
[Phase 0] 수직 권한 상승 검사       일반 계정(A)으로 관리자 API를 직접 찔러봄
        ↓ (관리자 API만 검사하는 모드면 여기서 종료)
[Phase 0.5] 상대방(B)의 진짜 id 알아내기   B 계정의 식별자를 3단계로 추적
        ↓ (일반 계정이 1개뿐이면 여기서 종료 — IDOR엔 계정 2개 필요)
[Phase 1] 자원 인벤토리 수집 + 노이즈 제거   A와 B가 각각 볼 수 있는 자원을 모으고
                                        "둘 다 보이는 공개 자원"은 걸러냄
        ↓
[Phase 2] 수평 권한 상승(IDOR) 검사        A 토큰으로 B의 자원 id를 넣어 접근 시도
                                        (경로에 넣는 방식 / 숨은 쿼리로 찔러보는 방식)
        ↓
[Phase 4] Mass Assignment 검사            role류 파라미터에 관리자 값을 끼워 넣어
                                        요청 후, 응답에 그대로 반영됐는지 확인
        ↓
[정리] 테스트 중 새로 만든 자원 삭제
```

## 4. 각 단계 상세 설명

### 준비 단계

- 설정(`diagnosis_4_5`)에서 `probe_mode`(`base_only`/`sample`/`full`), `sample_size`, `timeout` 등을 읽는다.
- 테스트 계정 전부를 로그인시켜 **역할(role)로 ADMIN 그룹과 USER 그룹으로 나눈다.**
- **일반 계정이 하나도 없으면 스캔 자체를 건너뛴다** — 이 엔진은 관리자 계정만으로는 아무것도 검증할 수 없기 때문이다.
- api-tree(`api-tree-verified.json → api-tree-ready.json → api-tree.json` 순 폴백)에서 대상 엔드포인트를 가져오고, 경로에 `/admin/`이나 `/manage/`가 들어간 것을 "관리자 엔드포인트"로 미리 분류해둔다.

> ⚠️ **계정은 딱 두 명만 쓴다**: 등록된 계정이 몇 개든, 일반 계정 중 **딱 두 명(A=공격자 역할, B=피해자 역할)만** 골라서 그 둘 사이의 권한 경계를 확인한다. 관리자 계정은 "이 URL이 관리자 전용인지" 분류하는 데만 쓰이고, 실제 요청을 보내는 주체가 아니다.

### Phase 0 — 수직 권한 상승

관리자 엔드포인트마다, **일반 계정 A의 토큰으로** 그대로 요청을 보내본다. "성공"으로 판정하는 기준은 단순히 상태 코드가 아니라 두 가지를 같이 본다.

- 응답 상태가 성공 계열(200/201/204)이면서
- 응답 본문에 "권한 없음", "denied", "forbidden" 같은 **에러를 암시하는 단어가 없을 때**

`probe_mode`가 "관리자 API만 검사"로 설정돼 있으면 여기서 스캔을 끝낸다.

### Phase 0.5 — 상대방(B)의 진짜 식별자 찾기

이후 단계(IDOR)를 하려면 "B의 자원"을 콕 집어 가리킬 수 있는 값이 필요하다. 근데 로그인 계정 목록에 적힌 id가 항상 그 용도로 쓸 수 있는 값이라는 보장이 없다(예: UUID는 URL 경로에 잘 안 쓰인다). 그래서 3단계로 추적한다.

1. 계정 정보에 있는 id를 써본다 — 단, UUID처럼 생겼으면 건너뛴다.
2. `/me`, `/profile` 같은 "내 정보" 엔드포인트를 직접 호출해서 응답에서 id류 필드를 찾는다.
3. 그것도 안 되면 로그인 토큰(JWT) 자체를 까서 그 안에 든 사용자 식별자를 꺼낸다.

**일반 계정이 2명 미만이면 여기서 스캔을 끝낸다** — 수평 권한 상승은 "다른 사람"이 있어야 성립하는 검사라서다.

### Phase 1 — 자원 인벤토리 수집 + 노이즈 제거

A와 B 각각으로 로그인해서, 파라미터 없이 부를 수 있는 목록형 API들을 돌며 응답에 나오는 모든 id류 값을 긁어모은다. 이렇게 두 계정의 "보이는 자원 목록"을 각각 만든 다음, **B에서는 보이는데 A에서는 안 보이는 id만** 골라낸다.

> 왜 이 필터링이 필요한가: 게시판처럼 **모두에게 공개된 자원**은 A도 B도 똑같이 볼 수 있다. 이런 공개 자원 id로 IDOR을 테스트하면 "접근 성공"이 나와도 당연한 결과라 의미가 없다. **A는 못 보는데 B만 보이는 자원**이어야 "B 개인 소유 자원"이라고 볼 수 있고, 그걸 A가 열 수 있으면 진짜 문제다.

목록 조회만으로 아무것도 못 찾으면, **직접 글쓰기 등으로 B 소유 자원을 하나 만들어서** 테스트 재료를 확보한다(추후 정리 단계에서 삭제).

### Phase 2 — 수평 권한 상승(IDOR) 검사, 2가지 방식

### XSS/CSRF와 다르게, 4-5는 "권한 경계 검사 기법"별로 판정 기준이 다르다

<aside>

**1. Vertical PrivEsc — "성공 응답 + 에러 문구 없음이면 의심"**

**원리:** 일반 계정 토큰으로 관리자 API를 직접 호출. 응답이 성공 계열이고 에러를 암시하는 단어가 없으면 뚫린 것으로 본다.

**양호로 판정되는 경우:**
- 401/403처럼 명확한 거부 응답이 옴.
- 200이 오더라도 본문에 "권한 없음"류 문구가 포함돼 있음 (서버가 상태코드는 200으로 주지만 사실상 거부하는 케이스를 잡기 위한 보정).

**한계:** 반대로, 서버가 진짜 에러 상황(예: 리다이렉트)을 200으로 잘못 반환하는 구현이면 오탐이 날 수 있다. 그래서 이 finding엔 항상 "포스트맨으로 직접 호출해서 실제로 관리자 데이터가 보이는지 눈으로 확인하라"는 수동 검증 안내가 같이 붙는다.

---

**2. IDOR Case 1 — 경로에 박힌 id를 바꿔치기**

**원리:** `/orders/{id}` 처럼 경로 안에 자원 id가 들어가는 엔드포인트를 골라, 그 자리에 **B 소유로 확인된 id**를 넣고 **A의 토큰**으로 요청한다. 200이 오면 의심.

**양호로 판정되는 경우:**
- 403/404가 정상적으로 옴 (서버가 "이 자원이 당신 것 맞습니까"를 제대로 검증하고 있다는 뜻).

**한계:** 애초에 아무나 봐도 되는 공개 게시글 같은 자원이면 200이 나와도 문제가 아니다. Phase 1의 노이즈 제거로 상당 부분 걸러지지만, 완전하지는 않아서 "비즈니스 맥락상 원래 공개된 자원인지"는 사람이 최종 확인해야 한다.

---

**3. IDOR Case 2 — 숨은 쿼리 파라미터로 찔러보기 (의미론적 비교 방식)**

**원리:** 경로에 id가 없는 GET API(`/my-page` 같은 "내 정보" 계열)에 대해, `userId`, `memberId` 같은 흔한 파라미터 이름을 A의 토큰으로 **강제로 붙여서** 요청해본다. 이때 판정은 상태 코드가 아니라 **"응답 안에 B의 신원 정보가 새로 나타났는가"**로 한다.

**판정 절차:**
1. 파라미터를 붙이지 않은 A의 원래 응답에 B의 식별자(id/이메일/닉네임)가 **원래부터 있었는지** 먼저 확인한다.
2. 원래 없었는데, 파라미터를 주입한 뒤 응답에 B의 식별자가 **새로 나타나면** → 취약.
3. 원래부터 있었다면 → 애초에 공개된 정보이므로 무시.

**양호로 판정되는 경우:**
- 파라미터를 넣어도 B의 정보가 전혀 안 나타남.
- B의 정보가 나타나긴 했지만, 파라미터 없이 요청했을 때도 이미 보이던 정보였음(공개 데이터).

**왜 이 기법이 필요한가 (설계의 핵심):** 처음엔 "이 API가 개인화된 API인지"를 사전에 스키마 비교로 먼저 판단하고, 그런 API로 분류된 것만 골라서 찔러보는 방식이었다. 그런데 이 사전 판단 로직 자체가 오탐과 누락을 동시에 만들었다. 그래서 **사전 판단을 없애고, 일단 무조건 찔러본 뒤 "응답이 실제로 달라졌는가"만으로 판단**하는 방식으로 바꿨다. 판단 기준을 앞단(추측)이 아니라 뒷단(실제 관찰)에 두는 게 훨씬 정확했다.

---

**4. Mass Assignment — "응답에 주입한 값이 그대로 반영됐는가"**

**원리:** 회원가입/수정 같은 쓰기 요청에서 `role`, `admin`, `authority`처럼 권한을 암시하는 이름의 파라미터를 찾아, 거기에 `"ADMIN"`, `"ROLE_ADMIN"` 같은 값을 끼워 넣어 보낸다.

**판정 절차:** 단순히 요청이 성공(200/201)했다고 취약으로 보지 않는다. **응답 본문 안에 그 파라미터와 주입한 값이 그대로 되돌아오는지**를 재귀적으로 확인해야만 확정한다.

**양호로 판정되는 경우:**
- 요청은 성공했지만 응답에 주입한 role 값이 안 보임 (서버가 해당 필드를 무시하고 안 받았을 가능성이 높음).

**한계 (반드시 감안해야 할 부분):** 응답에 값이 그대로 보인다고 해서 **DB에 실제로 그렇게 저장됐다**는 보장은 아니다. 서버가 "받은 값을 그냥 그대로 화면에 돌려주기만 하고, 저장은 원래 로직대로" 하는 경우에도 같은 현상이 나타날 수 있다. 그래서 최종 확인은 "그 계정으로 다시 로그인해서 실제로 관리자 권한이 생겼는지"를 사람이 확인해야 한다.

</aside>

### 정리(Cleanup) 단계

Phase 1에서 테스트를 위해 새로 만든 자원이 있다면, 스캔이 끝난 뒤 B 계정 권한으로 전부 삭제한다. 진단 때문에 대상 서비스에 테스트 쓰레기가 남지 않도록 하기 위함이다.

---

## 5. 오탐(false positive) 방지 장치

- **Vertical**: 상태 코드만이 아니라 응답 본문의 에러 키워드까지 같이 확인.
- **Discovery 노이즈 제거**: A도 볼 수 있는 자원은 "공개 자원"으로 보고 IDOR 후보에서 제외.
- **Case 2 의미론적 비교**: 원래 응답에 이미 있던 정보면 "노출"로 안 침 — 진짜 새로 유출된 것만 잡는다.
- **Mass Assignment 응답 확인**: 요청 성공만으로 판정하지 않고, 응답에 주입값이 실제로 반영됐는지까지 재귀적으로 확인.
- **모든 finding에 "수동 검증 필수" 안내 동봉**: 자동 판정을 100% 확정으로 취급하지 않고, 사람이 최종 확인할 수 있게 각 finding에 "왜 오탐일 수 있는지"와 "어떻게 수동으로 재현하는지"를 같이 남긴다.

> 이 엔진은 전체적으로 **정밀도(precision)보다 재현율(recall)을 우선**하는 설계다. 애매하면 일단 "의심"으로 올리고, 최종 판단은 사람이 하도록 넘긴다.

## 7. 개발하면서 실제로 겪었던 문제와 해결

1. **최초 구현**: 관리자 API 직접 접근 검사(Vertical)와 기본적인 IDOR/Mass Assignment 탐지를 갖춘 형태로 처음 만들어졌다.

2. **토큰 인증만 지원하다가 쿠키 세션 인증도 지원하도록 확장**: 초기 버전은 인증을 "토큰 문자열 하나"로만 다뤘는데, 세션 쿠키 기반으로 로그인하는 플랫폼에서는 이 방식이 안 먹혔다. → 인증을 헤더 딕셔너리 단위로 주고받도록 바꿔서, 토큰이든 쿠키든 같은 방식으로 다룰 수 있게 일반화했다.

3. **IDOR Case 2의 판정 로직을 완전히 뒤집었던 리팩터링**: 처음엔 "이 API가 개인화된 API인지"를 A/B 응답의 스키마(구조)를 비교해서 먼저 분류하고, 그렇게 분류된 API에만 파라미터를 주입하는 2단계 방식이었다. 그런데 이 사전 분류 자체가 부정확해서, 진짜 취약한 API를 건너뛰거나 반대로 엉뚱한 걸 의심하는 문제가 있었다. → 사전 분류를 없애고 **"일단 무조건 찔러본 뒤, 응답에 상대방 정보가 실제로 새로 나타났는지"만으로 판정**하는 방식(의미론적 비교)으로 완전히 바꿨다. 이 변경 이후 예전 분류용 헬퍼 함수들은 코드에서 안 쓰이게 됐다.

4. **능동 자원 생성 순서 문제**: 원래는 수동 조회로 자원을 못 찾으면 곧바로 "글쓰기 등으로 자원을 만들어서" 테스트 재료를 확보했는데, 이 시점이 노이즈 제거보다 앞서 있어서 불필요하게 자원을 계속 새로 만드는 비효율이 있었다. → 노이즈 제거까지 끝낸 뒤에도 여전히 후보가 없을 때만 능동 생성하도록 순서를 조정했다.

5. **Docker 환경에서 대상 주소가 안 맞던 문제**: 로컬 개발 환경 기준 주소(`localhost`)를 그대로 쓰다 보니 Docker 컨테이너 안에서 대상 서버에 접근이 안 됐다. → 모든 요청 URL을 공용 주소 변환 함수에 통과시켜서 Docker 환경에서도 동작하도록 수정했다.

6. **로그가 스캔을 반복할수록 계속 쌓이던 문제**: 실행 로그 파일이 스캔마다 이어 붙기만 해서 시간이 지날수록 파일이 계속 커졌다. → 스캔을 시작할 때마다 로그 파일을 초기화하도록 수정. 인벤토리 목록을 로그에 통째로 찍던 부분도 상위 몇 개만 남기도록 줄였다(로그 폭탄 방지).

7. **타임아웃 등 세부 설정값이 코드에 고정돼 있던 문제**: 요청 타임아웃, 스캔 범위(`probe_mode`), 최대 엔드포인트 수 같은 값들이 전부 코드 안에 하드코딩돼 있어서 상황에 따라 조정할 수 없었다. → 이 값들을 진단 옵션으로 빼서 설정에서 조절할 수 있게 만들고, 잘못된 값이 들어오면 안전한 범위로 보정하는 검증 로직도 같이 추가했다.

## 8. 알려진 한계

- **모든 계정을 다 돌지 않는다** — 등록된 계정이 몇 개든, 일반 계정 중 딱 두 명만 골라서 그 둘 사이의 권한 경계만 확인한다. 계정이 3개 이상이어도 나머지는 검사에 관여하지 않는다.
- **모든 finding이 "수동 검증 필수"다** — 정밀도보다 재현율을 우선하는 설계라, 자동 판정 결과를 그대로 확정으로 쓸 수 없고 반드시 사람이 한 번 더 확인해야 한다.
- **탐지 로직 자체에 대한 자동 테스트가 없다** — 현재 있는 테스트는 "설정값이 올바르게 전달되는지"만 확인하고, 실제 IDOR/Mass Assignment 판정이 정확한지는 자동으로 검증되지 않는다.
- **모듈 메타데이터의 엔진 표기가 실제 구현과 다르다** — 메타데이터에는 엔진이 다르게 표기돼 있지만, 실제로는 ZAP 연동 없이 직접 HTTP 요청만으로 동작한다. 사소하지만 헷갈릴 수 있는 부분.
- **오래된 리팩터링의 흔적(죽은 코드)이 일부 남아있다** — Case 2 판정 방식을 통째로 바꾸면서 예전 방식에서 쓰던 헬퍼 함수 일부가 더 이상 호출되지 않는 채로 남아있다.

## 9. 예상 면접 질문 & 답변 포인트

**Q. 권한 상승 취약점을 어떻게 자동으로 검증하나요?**
> 관리자 API를 일반 계정 토큰으로 직접 호출해보는 수직 검사, 그리고 계정 두 개(A, B)를 두고 A가 B의 자원에 접근할 수 있는지 확인하는 수평(IDOR) 검사, 마지막으로 쓰기 요청에 role 같은 파라미터를 몰래 끼워 넣어 서버가 그대로 받아주는지 확인하는 Mass Assignment 검사, 이렇게 세 가지를 실제 HTTP 요청으로 수행합니다.

**Q. IDOR을 탐지할 때 오탐은 어떻게 줄였나요?**
> 두 가지 장치가 있습니다. 하나는 사전 필터링인데, A와 B 둘 다 볼 수 있는 자원(공개 데이터)은 애초에 테스트 대상에서 제외합니다. 다른 하나는 판정 시점의 의미론적 비교인데, 파라미터를 주입하기 전 응답에 이미 상대방 정보가 있었다면 원래 공개된 정보로 보고 무시하고, 주입 후에만 새로 나타난 경우만 취약으로 판정합니다. 처음엔 API를 "개인화된 API인지" 사전에 분류하는 방식이었는데, 그 분류 자체가 부정확해서 지금 방식으로 바꿨습니다.

**Q. Mass Assignment는 왜 상태 코드만으로 판정하지 않나요?**
> 요청이 성공(200/201)했다고 해서 서버가 실제로 그 값을 저장했다는 보장이 없기 때문입니다. 그래서 응답 본문에 주입한 파라미터와 값이 그대로 반영돼 있는지까지 재귀적으로 확인해야만 취약으로 확정합니다. 다만 이것조차도 "응답에 에코백만 되고 실제 저장은 안 될" 가능성이 있어서, 최종 확인은 실제로 재로그인해서 권한이 바뀌었는지 사람이 봐야 한다고 안내합니다.

**Q. 개발하면서 가장 크게 바꾼 설계는?**
> IDOR의 숨은 쿼리 파라미터 탐지 로직입니다. 원래는 "이 API가 개인정보를 다루는 API인지"를 응답 구조 비교로 먼저 판단하고, 그렇게 분류된 것만 테스트하는 2단계 방식이었는데, 이 사전 판단 자체가 정확하지 않아서 놓치거나 잘못 의심하는 경우가 많았습니다. 그래서 사전 판단을 없애고, 일단 전부 찔러본 뒤 "응답에 상대방 정보가 실제로 새로 나타났는가"라는 결과만으로 판정하도록 바꿨습니다. 판단 기준을 예측이 아니라 관찰로 옮긴 게 핵심이었습니다.
